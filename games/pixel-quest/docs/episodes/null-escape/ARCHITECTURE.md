# «Побег Нулика»: Phase 1–7

Архитектура и выполнение первых двух фаз согласованы владельцем 2026-09-30. Полное [ТЗ](SPEC.md) описывает будущую игру; оно не означает готовность всех сцен. Этот onboarding является отдельным сценарием, а не заменой Episode 01 «Первый сбой» или технической «AR Инициации».

## Реализованный объём

`START → SCAN → терминал + Нулика + кнопка → предупреждения → TOUCH → авария + портал → NULL_LOST → DISCOVER → NULL_FOUND → COLLECT → NULL_ASSEMBLED → CHOOSE → CORE_FOUND → SEQUENCE → PORTAL_CLOSING → ANOMALY_EVENT → ENDING → COMPLETED`.

Открытие: `?episode=null-escape`. Без параметра запускается Episode 01; `?episode=ar-initiation` запускает прежние шесть упражнений. Начало по кнопке «Начать» одновременно разрешает Web Audio. Доступ к камере по-прежнему запрашивает существующий AR-движок.

Состояния сценария после запуска: WAITING_START_MARKER → NULL_INTRO → WAITING_RED_BUTTON → ACCIDENT → NULL_LOST → SEARCHING_NULL → NULL_FOUND → COLLECTING_PARTS → ASSEMBLING_NULL → NULL_ASSEMBLED → CHOOSING_CORE → CORE_FOUND → SEQUENCE_ACTIVE → SEQUENCE_SOLVED → PORTAL_CLOSING → ANOMALY_EVENT → ENDING → COMPLETED. До START runner находится в READY. У каждого снимка есть отдельные scene_id, scene_phase, mechanic, history, run_id. COMPLETE означает завершение всего сценария; сюжетный state — COMPLETED.

## Переиспользованные компоненты

Точка входа games/pixel-quest/app.js выбирает компонент; platform/ar/register-game.js сохраняет существующий запуск A-Frame/8th Wall и набор image targets. marker-manager обрабатывает xrimagefound/updated/lost. ar-object-manager хранит последний якорь и корректирует его по повторному наблюдению. Новый сценарий использует те же AR-01 SCAN, AR-03 TOUCH, registry, event-bus, game-clock, raycast-adapter, quest-ui и pixel-audio.

Второго gameplay-runner нет: scenario-runner оборачивает существующую механику в scene-runtime только для сцен с enter/exit. Обычные шаги прежних сценариев остаются совместимыми. Граф переходов по-прежнему проверяется до запуска.

## Повтор, ввод и пауза

До завершения всех трёх предупреждений TOUCH заблокирован в scene-runtime и AR raycast. Красная кнопка начинает пульсировать после последней реплики. Прямого задания нажать её нет. Через 15 секунд бездействия появляется фраза «Ты ведь не собираешься её нажимать?..». SCAN имеет подсказку через 15 секунд. Жёсткого таймаута или Game Over у этих INTRO-шагов нет; общий time_limit механик сохранён для других конфигураций.

«Повторить сцену» создаёт новый run_id, отменяет таймеры/эффекты прежней попытки, восстанавливает объекты и сохраняет результат SCAN. После конца фрагмента повтор также доступен. «Сначала» очищает историю. Скрытие страницы останавливает игровое время и звук; возвращение продолжает текущую текстовую последовательность. Удаление компонента очищает UI, объекты, подписки и таймеры.

Диалоги сейчас рассчитаны прежде всего на текст. Новый view принудительно показывает реплику, прокрутка текстовой области возвращается наверх. Уже существующая опциональная speechSynthesis доступна, но тайминг сцены пока не ждёт окончания синтеза: голос может обрываться при следующей реплике. Финальный voice-over и его синхронизация — отдельная доработка. Размер нижней панели остаётся ≤1/5 viewport.

## Debug и события

Обычная сборка: `npm run build`. Отладочная: `npm run build -- --env debug=true`. Флаг __AR_DEBUG__ задаётся при сборке, URL не включает отладку в обычном bundle. Перед публикацией используется обычная сборка.

Панель показывает state, сцену, фазу, mechanic_id и progress. GO запускает выбранную сцену, RETRY повторяет её, NEXT переходит к следующей успешной ветке, если она существует. Отладочный переход очищает историю и не подделывает результаты предыдущих механик. При прямом запуске red_button всё равно нужно показать маркер камере: выдуманных мировых координат нет. Для финальной сцены NEXT не действует.

В консоль через необязательный sink поступают scenario_started, marker_detected, red_button_pressed, null_discover_started, null_found, collect_started, part_collected, collect_completed, choose_started, wrong_core_selected, correct_core_selected, sequence_started, sequence_failed, sequence_completed, anomaly_event_started, scenario_completed. Поля: timestamp ISO UTC, scenario_id, scene_id, mechanic_id, attempt, duration_ms текущей сцены, scenario_duration_ms, session_id, run_id, scenario_state. Повтор сцены увеличивает attempt в пределах сеанса; ранние/повторные нажатия не создают red_button_pressed. Исключение наблюдателя не останавливает игру. Внешняя отправка/хранилище не подключены; события будущих сцен не имитируются.

## Ограничения и следующий этап

Реализован полный сюжетный путь шести MVP-механик и финала. Целевая длительность 8–12 минут и самостоятельное прохождение детьми ещё должны быть проверены в Phase 8; автоматические тесты не подтверждают эти UX-цели.

Привязка остаётся маркерной с последней известной позой и повторной коррекцией; постоянная карта помещения не реализована. SLAM-дрейф вне видимости маркера всё ещё возможен. Сохранение прогресса между перезагрузками отсутствует. Владелец подтвердил успешную проверку Phase 2–6 на телефоне. Phase 7 на физическом устройстве, детская UX-проверка и публикация ещё не проверены.


## Phase 3 — поиск Нулика

После аварии автоматически запускается discover_null на существующей AR-02 DISCOVER. Две реплики из ТЗ занимают 7,4 секунды подготовки. Затем появляется отдельный null_head с маркерным смещением x=2.5, y=0.55, z=0 (справа от терминала), панель сворачивается, показываются рамка и короткая подсказка. Полная модель Нулика остаётся скрытой. Терминал и портал сохраняются как ориентиры.

Условие успеха: центр видимой, не перекрытой головы находится в рамке непрерывно 500 мс. Касание головы не завершает DISCOVER. При потере вида, длинном перерыве кадров, паузе или новой попытке отсчёт начинается заново. Адаптер не подтверждает обнаружение в PREPARING/PRESENTING: это предотвращает потерю единственного подтверждения до запуска механики.

Параметры собраны в games/pixel-quest/episodes/null-escape/search-config.js: target_id, hold_ms, search_radius, задержки и уровни подсказок. Через 15 секунд активного поиска — текст и звуковой сигнал; через 25 — динамический указатель влево/вправо/вверх/вниз; через 40 — белая подсветка пульсирующей головы и более явная подсказка. Сигнал обычный, не пространственный звук. Для определения направления используется platform/ar/direction-adapter.js: положение цели относительно камеры, включая цель за спиной. Направление помогает искать, но само по себе не засчитывает обнаружение и не проверяет перекрытие.

Указатель выводится через ui.searchHint() рядом с центральной рамкой и виден при свёрнутой панели. Кнопка «Показать инструкцию» открывает текст и «Повторить сцену». Успех возвращает панель, подсвечивает голову и запускает «Нашёл!» → «Только не спрашивай, где остальное.». После 5,3 секунды начинается сцена COLLECT с диагностикой частей.

Повтор поиска восстанавливает только эту сцену, сбрасывает подсказки и сохраняет результаты SCAN/TOUCH. При прямом отладочном входе нужно показать маркер для размещения объектов. События null_discover_started и null_found обозначают начало активного поиска и принятое обнаружение; duration_ms по-прежнему считает всю сцену, включая подготовительные реплики. Разность scenario_duration_ms этих двух событий даёт активную длительность поиска без вводных реплик и фоновой паузы.


## Phase 4 — сбор деталей и восстановление Нулика

`collect_parts` использует существующую AR-05 COLLECT без изменения её правил. Входная последовательность показывает голову, терминал и портал и четыре реплики из ТЗ: «Портал раскидал мои детали по этому сектору.» → «Обычно я собираю себя сам.» → «Но сейчас у меня небольшая техническая проблема.» → «У меня нет рук.». Подготовка занимает 12 секунд; до её окончания сбор заблокирован.

Конфигурация `games/pixel-quest/episodes/null-escape/collect-config.js` содержит три сюжетных ID: null_body (двигатель), null_left_arm, null_right_arm, их подписи, цвета, визуальные типы, позиции и задержки подсказок. Эти ID — контент общей COLLECT, а не новые механики. requiredParts определяется длиной списка; собирать можно в любом порядке. Детали расположены компактно возле головы относительно START_MARKER: двигатель (1.8, 0.5, 0.25), левая рука (2.5, 1.25, 0.15), правая рука (3.2, 0.65, 0.2). Сбор выполняется нажатием на видимую деталь без ограничения расстояния: подход к стене не требуется.

При начале механики общий AR-адаптер показывает детали из кеша позы маркера. Каждое принятое нажатие скрывает деталь, увеличивает счётчик 0/3 → 3/3, отмечает её в диагностике и воспроизводит звуковой сигнал. Уже собранные детали удалены из множества размещённых объектов и не возникают при повторном обнаружении маркера. Нажатия на голову и другие объекты не засчитываются. Нет таймаута, штрафов и Game Over.

Через 15 секунд активного сбора появляется текстовая подсказка, через 30 — подсветка оставшихся деталей. Таймеры считаются от начала механики, а не от последнего нажатия. Фоновая пауза сохраняет частичный результат; «Повторить сцену» очищает только текущий сбор и восстанавливает все три детали, сохраняя SCAN/TOUCH/DISCOVER. Полный restart по-прежнему сбрасывает весь сценарий.

После третьей детали запускается ASSEMBLING_NULL: отдельная голова скрывается, на её месте появляется null_assembled с головой, двигателем и обеими руками из GLB. Временный эффект появления длится 1 секунду, затем state становится NULL_ASSEMBLED и звучат/показываются «Есть!», «Руки!», «Никогда не думал, что буду так рад собственным рукам.». Завершающая последовательность занимает 8 секунд. Это презентация результата COLLECT, не реализация AR-09 ASSEMBLE.

События collect_started, part_collected (с target_id) и collect_completed можно наблюдать через существующий необязательный telemetry sink. collect_completed обозначает принятие всех трёх деталей; переход к CHOOSE выполняется после окончания реплик сборки. Финальный экран следует после сюжетной сцены Phase 7.


## Phase 5 — выбор настоящего энергокуба

Сцена choose_core использует существующую AR-06 CHOOSE с неограниченными попытками, без таймаута и штрафа. После восстановления Нулика следуют четыре реплики: «Вот это плохо.» → «Нам нужен мой настоящий энергокуб.» → «Подделки нестабильны.» → «Настоящий куб всегда пульсирует два раза подряд.». Подготовка занимает 11,2 секунды; ранние нажатия заблокированы. Затем появляются четыре одинаковых по цвету куба над персонажем.

`games/pixel-quest/episodes/null-escape/choose-config.js` содержит correctCore (по умолчанию core_03), позиции и ритмы. Правильный ритм вычисляется по correctCore, поэтому смена правильного ID одновременно меняет условие CHOOSE и визуальный паттерн. Все циклы длятся 2320 мс: правильный — два импульса по 300 мс с промежутком 220 мс и длинной паузой 1500 мс; ложные — один короткий, три коротких и один длинный импульс. Амплитуда масштаба 30%. Цвет не подсказывает правильный ответ.

Общий `platform/ar/pulse-pattern.js` анимирует только визуальный дочерний объект. Якорь остаётся неподвижным. Ритмы считаются от активного времени runner; скрытие страницы останавливает фазу. reset восстанавливает исходный масштаб. Отдельный игровой `choice-presentation.js` связывает ритмы, UI и обратную связь, не проверяя правильность ответа — это остаётся задачей CHOOSE.

Неверный выбор приглушает цвет выбранного куба, воспроизводит denied и показывает «Не он! Ничего страшного, попробуй ещё.». Куб сохраняет свой ритм и остаётся доступным, ошибаться можно повторно. Нажатия на другие объекты не засчитываются. Подсказки через 15 и 30 секунд активного выбора напоминают правило, не раскрывая номер куба.

Верный выбор подсвечивает куб, останавливает ритмы и переводит state в CORE_FOUND. После реплик «Есть!» и «Вот теперь я снова почти гениален.» (5 секунд) начинается SEQUENCE. «Повторить сцену» сбрасывает только выбор, восстановляет цвета и ритмы и сохраняет результаты SCAN/TOUCH/DISCOVER/COLLECT. События choose_started, wrong_core_selected и correct_core_selected дополняют существующий журнал; target_id указывает выбранный куб. phase6_completed обозначает конец текущего фрагмента, а не всей игры.

SEQUENCE с символами закрытия портала и финальная сцена подключены ниже; следующий этап — итоговая QA-проверка.


## Phase 6 — последовательность символов

Сцена portal_sequence использует существующую AR-07 SEQUENCE и общий sequence-presenter без изменения gameplay платформы. После CHOOSE появляются реплики «Сейчас портал покажет код закрытия.» и «Запомни его.» (5 секунд подготовки), затем четыре геометрически разных символа: ромб, круг, треугольник, квадрат. Они одинакового цвета, различаются формой и русскими подписями во время показа.

`games/pixel-quest/episodes/null-escape/sequence-config.js` содержит символы, позиции, последовательность и интервалы. По умолчанию: ромб → треугольник → круг. Перед показом общая задержка 1000 мс; каждый символ подсвечен 800 мс, затем пауза 400 мс. Ввод открывается только после всего показа (4,6 секунды при готовой геометрии). Пока геометрия не готова, общий presenter ждёт её.

`sequence-presentation.js` отвечает за тексты, кнопки и звук принятого ввода. Во время SHOWING ранние нажатия не засчитываются. В INPUT отображается «ПОВТОРИ ПОСЛЕДОВАТЕЛЬНОСТЬ» и прогресс 0/3 → 3/3. Ошибка показывает «Почти. Давай ещё раз.» и автоматически запускает полный показ, без Game Over и лимита попыток. REPLAY («Показать ещё раз») очищает текущий префикс и повторяет показ без штрафа. RETRY повторяет всю текущую сцену с вводными репликами, сохраняя пять предыдущих результатов.

При скрытии страницы подсветка снимается; при возвращении общий presenter запрашивает новый показ с новым token. Старый token/run_id не может разрешить ввод в новой попытке. После верного ввода state становится SEQUENCE_SOLVED, проигрываются/показываются «Получилось!» и «Я даже начинаю подозревать, что ты сделал всё это специально.» (6 секунд), затем state PORTAL_CLOSING и автоматический переход к финальной сцене.

PORTAL_CLOSING передаёт управление финалу Phase 7. События sequence_started, sequence_failed (ошибка ввода, не завершение игры) и sequence_completed сохраняются; полное завершение теперь обозначает scenario_completed.


## Phase 7 — портал, Аномалия и финал

`portal_finale` — presentation-сцена существующего runner, без нового mechanic_id. Она содержит последовательность команд в finale-config.js; тексты finaleDialogues подключены в общий каталог реплик. Новые файлы finale-presentation.js и terminal-display.js обслуживают экранный glitch и надписи на физически привязанном AR-терминале. Игровые механики не содержат этой сюжетной логики.

Финал длится 41,35 секунды активного времени. Первые 4 секунды UI предлагает посмотреть на портал и терминал у карточки огня. Далее стабильность 82% → 91% → 97% → 99%, остановка и реплики «Странно.» / «Почему 99?». Состояние ANOMALY_EVENT вызывает изменённый пиксельный звук, короткое экранное искажение и безликий силуэт внутри портала на 450 мс. Его природа не объясняется.

После «Ты это видел?» терминал показывает «СПАСИБО ЗА ДОСТУП». После «Это написал не я.» надпись меняется на «УВИДИМСЯ.», портал скрывается мгновенно. Сообщения продублированы в UI. Кириллица рисуется canvas-текстурой на плоскости терминала, без внешних шрифтов и загрузок. Для неё AR object manager принимает опциональный cleanup, возвращаемый createVisual; при dispose освобождаются texture/material/geometry.

После паузы Нулика произносит заключительные реплики из ТЗ. «ОБУЧЕНИЕ ЗАВЕРШЕНО» на 650 мс заменяется «СВЯЗЬ УСТАНОВЛЕНА» с glitch и возвращается. Последняя реплика — «…Мне это совсем не нравится.». Только после неё runner завершается, state становится COMPLETED и публикуется scenario_completed. anomaly_event_started публикуется при вступлении в ANOMALY_EVENT. Для presentation-сцены mechanic_id в аналитике равен null.

Все задержки используют game-clock: фон останавливает последовательность, звук и экранное искажение; возврат продолжает оставшееся время. «Повторить сцену» сбрасывает только финал, очищает текст терминала/glitch/силуэт и сохраняет шесть результатов механик. На финальном экране можно повторить финал или начать всю игру сначала. После закрытия портала повторное наблюдение маркера не возвращает его до явного повтора сцены.

Графика силуэта и glitch — временные эффекты MVP. Карта помещения, новые механики, сервер и сохранения не добавлялись. Следующая фаза — Phase 8: полный проход на устройствах, повторы, ошибки, маркеры, звук, производительность и UX.

## Модель Нулика

В начальной сцене и после COLLECT используется `games/pixel-quest/assets/Nulik-mobile.glb` (2 862 треугольника, встроенные текстуры). GLTFLoader загружает и разбирает модель один раз при инициализации сценария до сканирования. Полный персонаж, голова и детали используют общий шаблон, геометрию и текстуры, но независимые узлы трансформаций. До готовности отображается «Загружается Нулик…», без старой геометрической заглушки; при ошибке появляется предложение обновить страницу. После готовности уведомление скрывается. Журнал тестового ngrok показал передачу исходного GLB на телефон за 35,4 секунды; код HTTP 200 сам по себе не подтверждает успешный разбор и отображение модели на устройстве. Голова и собираемые детали извлекаются из соответствующих мешей нового GLB. Встроенный клип ROOTAction сохранён в файле, но автоматически не проигрывается.

`games/pixel-quest/episodes/null-escape/nulik-model.js` центрирует модель и ограничивает её максимальный габарит 0,7 единицы маркера. При первом видимом появлении масштаб дополнительно уменьшается до не более 35% ширины и высоты viewport по проекции габаритов через текущую AR-камеру. Это базовая калибровка; по запросу владельца от 2026-10-09 её результат дополнительно умножается на 2 по всем осям (modelScaleMultiplier в nulik-model.js). По последнему запросу размер уменьшен на треть относительно версии ×3 и больше не ограничивается 35% viewport. Размер сохраняется при повторах и после сборки; при дальнейшем приближении камеры экранный размер естественно растёт. Нормализация находится во вложенном объекте, поэтому эффекты исчезновения и сборки не сбрасывают масштаб. Проверка браузером использует настоящую GLB и синтетический маркер; размер, материалы и положение на физическом телефоне требуют проверки.

### Облегчённые текстуры

Рабочая модель `games/pixel-quest/assets/Nulik-mobile.glb` занимает 2 419 108 байт вместо 7 669 624 байт исходной `games/pixel-quest/assets/Nulik.glb`: уменьшение на 68,5% (в 3,17 раза). Все три встроенные текстуры уменьшены с 2048×2048 до 1024×1024. Цвет сохраняется в JPEG quality 88 с цветовой субдискретизацией 4:4:4; normal и metallic/roughness — в PNG без дополнительного сжатия с потерями после уменьшения разрешения. Новые расширения glTF и декодеры не нужны. Геометрия, анимационные буферы, узлы и параметры материалов сохранены; исходный GLB не изменён. Текущий масштаб задаётся в nulik-model.js (×2 после уменьшения на треть).

Повторная подготовка: `npm.cmd install --prefix tmp/nulik-tools --no-package-lock --no-save sharp`, затем `node scripts/optimize-nulik.cjs`. Вспомогательный Sharp устанавливается в игнорируемую временную папку и не входит в зависимости игры. Скрипт проверяет структуру GLB, размер текстур, побайтовую сохранность всех нетекстурных bufferViews и неизменность прочих разделов JSON.

Пройдены полный браузерный сценарий с облегчённой моделью, загрузка обеих версий через HTTP со штатным декодированием изображений Chrome, визуальное сравнение и сборка. Снижение объёма передачи не гарантирует пропорционального ускорения: скорость сети и декодирование текстур требуют повторного замера на телефоне.

### Четыре части и портал

`games/pixel-quest/episodes/null-escape/nulik-parts.js` извлекает Mesh_HEAD, Mesh_BODY, Mesh_L_HAND и Mesh_R_HAND. Двигатель — нижний блок Mesh_BODY. Исходная иерархия вычисляется без маркерной позы, её мировые матрицы переносятся на четыре независимых узла, сохраняя исходный вид. Имя GLTFLoader после удаления точек допускается через префикс Mesh_HEAD. Отдельная деталь центрируется по своему габариту, но нормализуется по габариту всего персонажа, поэтому её относительный размер сохраняется.

`games/pixel-quest/episodes/null-escape/nulik-breakup.js` обрабатывает сюжетное исчезновение null: первые 38% существующего эффекта длительностью 1100 мс части разлетаются, затем вращаются, уменьшаются и сходятся к центру портала. Используется время runner; пауза замораживает позы, повтор/смена сцены/удаление возвращают исходные трансформации. Существующая команда vanish перехватывается игровым presentation только для null; общая платформа и другие эффекты не изменены.

По явному согласованию владельца после DISCOVER головы COLLECT требует двигатель и две руки (3/3), без отдельного тестового энергомодуля. Механики, длительности реплик и порядок дальнейших сцен сохранены. Энергокубы CHOOSE не являются деталями модели и остаются отдельными объектами. Правила отражены в SPEC.md, критериях приёмки и подсказке.

### Встроенная левитация

Целый Нулик и null_assembled воспроизводят зацикленную ROOTAction из GLB. AnimationMixer вычисляет исходную иерархию, мировые трансформации мешей переносятся на независимые части без изменения маркерного якоря. Время берётся из runner: пауза останавливает левитацию. При начале разлёта поза левитации фиксируется, далее работают pivot-узлы портала. Отдельные поисковые детали статичны. При удалении модели mixer освобождается. Масштаб калибруется по исходным габаритам; анимация естественно меняет экранные габариты.

### Жесты во время реплик

Игровой nulik-gestures.js добавляет небольшие повороты и кивки головы и асимметричные движения рук поверх левитации. Жесты запускаются только для character-реплик по длительности команды dialogue; для ответов на ошибку CHOOSE/SEQUENCE используются короткие интервалы 2.8/2.2 секунды. Это сопровождение сюжетной реплики, не синхронизация с фактическими фонемами озвучки. Движения плавно набирают и снижают амплитуду, используют время runner и замирают на паузе. Во время поиска может двигаться только найденная голова; разбросанные руки остаются статичными. Перед разлётом жесты сбрасываются и не мешают порталу. Повтор, завершение, ошибка и удаление очищают состояние.

### GLB кнопки, портала и терминала

Вместо тестовой геометрии используются assets/button-mobile.glb, assets/portal-mobile.glb и assets/terminal-mobile.glb. prop-model.js заранее загружает все три файла, разделяет один разбор каждого URL между экземплярами и показывает статус загрузки/ошибки для видимых объектов. Поздний результат загрузки не прикрепляется после удаления. Существующие эффекты применяются к внешнему визуальному узлу; нормализация модели находится внутри. Кнопка развёрнута вокруг X на 90°, ширина 0.24; высота терминала 0.65, портала 0.87 в единицах маркера. Кнопка и текст финала размещены перед новым терминалом. Анимаций в предоставленных GLB нет.

Оптимизация: node scripts/optimize-props.cjs <каталог исходных GLB>. Нужен Sharp, как для optimize-nulik.cjs. Кнопка: текстуры 512×512; портал и терминал: 1024×1024 вместо исходных 2048×2048. Непрозрачный baseColor — JPEG quality 88, normal/metallic/roughness и изображения с альфа-каналом — PNG. Исходные файлы в Documents не изменяются. Скрипт проверяет побайтовую сохранность нетекстурных bufferViews и структуры остальных разделов GLB.
