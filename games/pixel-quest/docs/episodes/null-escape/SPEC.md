# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
# AR Pixel Quest — MVP-игра «Побег Нулика»

## 1. Задача

Необходимо реализовать первый onboarding-сценарий AR Pixel Quest для детей ориентировочно 8–12 лет.

Рабочее название:

**«Побег Нулика»**

Это не обычная инструкция по использованию AR, а короткая сюжетная игра, внутри которой пользователь естественным образом осваивает первые шесть базовых AR-механик проекта.

Используемые механики:

- `AR-01 SCAN`
- `AR-02 DISCOVER`
- `AR-03 TOUCH`
- `AR-05 COLLECT`
- `AR-06 CHOOSE`
- `AR-07 SEQUENCE`

Ориентировочная продолжительность прохождения:

**8–12 минут.**

Основная задача MVP:

проверить, может ли ребёнок без длительного объяснения взрослого понять базовую логику AR Pixel Quest и самостоятельно пройти последовательность игровых действий.

---

# 2. ВАЖНО ПЕРЕД НАЧАЛОМ РАЗРАБОТКИ

Сначала изучи существующий репозиторий AR Pixel Quest и текущую архитектуру проекта.

Не переписывай существующий рабочий код без необходимости.

Перед реализацией:

1. Найди текущую точку входа приложения.
2. Изучи существующую систему image targets / marker tracking.
3. Определи используемые A-Frame / 8th Wall компоненты.
4. Найди существующие обработчики появления/исчезновения маркеров.
5. Определи существующую структуру UI.
6. Определи, какие существующие компоненты можно переиспользовать.
7. Проверь существующую работу со звуком и анимациями.
8. Определи, как сейчас загружаются assets.
9. Не удаляй существующую функциональность, если она не конфликтует с новым сценарием.
10. Не реализовывай игру одним большим монолитным компонентом.

Перед внесением значительных изменений сначала предоставь:

- список существующих файлов, связанных с задачей;
- краткое описание текущей архитектуры;
- список файлов, которые потребуется изменить;
- список новых файлов;
- предлагаемую архитектуру сценария.

После этого можно переходить к реализации.

# 3. АРХИТЕКТУРНЫЙ ПРИНЦИП

Игра «Побег Нулика» не должна быть набором уникального hardcoded-кода.

Она должна использовать переиспользуемые игровые механики.

Желаемая концепция:

`Scenario`

→ `Scene`

→ `Mechanic`

→ `Success / Fail`

→ `Next Scene`

Игровая логика должна быть максимально отделена от:

- 3D-моделей;
- текстов;
- звуков;
- изображений;
- параметров сложности;
- конкретного сюжета.

Например, механика `COLLECT` должна впоследствии использоваться не только для частей Нулика, но и для:

- кристаллов;
- энергетических элементов;
- артефактов;
- существ;
- ключей;
- других игровых объектов.

## Цель

Подготовить пользователя к первому взаимодействию.

Игрок находится перед физическим AR-маркером Pixel Quest.

UI:

**«Наведи камеру на служебный терминал»**

При необходимости можно добавить простую визуальную рамку / индикатор поиска маркера.

Используемая механика:

`AR-01 SCAN`

---

# 7. СЦЕНА 1 — TERMINAL

## Trigger

AR marker успешно распознан.

## System Action

На маркере появляется AR-терминал.

Терминал должен появляться визуально заметно:

- короткая анимация появления;
- свечение;
- звук активации.

После появления терминала появляется персонаж Нуль.

---

# 8. ПЕРСОНАЖ NULL / «НУЛИК»

Нуль — цифровой помощник Pixel Quest.

Для MVP допустима упрощённая модель/placeholder.

Главное сейчас:

- логика персонажа;
- появление;
- реплики;
- реакция на события.

Не тратить значительное время на финальную модель персонажа до проверки gameplay.

Персонаж должен быть отдельной сущностью, чтобы впоследствии модель можно было заменить без изменения игровой логики.

---

# 9. ДИАЛОГ №1

После появления Нуля:

**Нуль:**

«О! Пользователь! Отлично.»

Пауза.

«Только ничего не трогай.»

Пауза.

«Особенно красную кнопку.»

После последней реплики красная кнопка терминала начинает слегка пульсировать.

---

# 10. СЦЕНА 2 — RED BUTTON

Используемая механика:

`AR-03 TOUCH`

Игрок должен нажать красную кнопку.

Важно:

никакого отдельного текста «нажмите кнопку» не показывать.

Сюжет должен сам провоцировать пользователя на действие.

Если пользователь ничего не делает длительное время, допускается дополнительная реплика Нуля:

«Ты ведь не собираешься её нажимать?..»

Кнопка при этом может начать светиться сильнее.

---

# 11. BUTTON EVENT

После нажатия:

1. кнопка реагирует;
2. воспроизводится звук;
3. терминал начинает давать glitch-эффект;
4. открывается портал;
5. начинается аварийное событие.

Нуль:

«Ты серьёзно?!»

«Я же буквально только что сказал её не нажимать!»

После этого портал начинает визуально воздействовать на сцену.

Нуль:

«Ой.»

Пауза.

«Это уже хуже.»

После этого:

**NULL DISASSEMBLE EVENT**

Нуль разлетается на четыре части из GLB: голову, двигатель и две руки. Части вращаются, втягиваются в портал и исчезают. При повторе сцены исходная поза восстанавливается.

# 12. СЦЕНА 3 — DISCOVER NULL

Используемая механика:

`AR-02 DISCOVER`

После аварии игрок слышит голос Нуля.

Нуль:

«Так… хорошие новости: я всё ещё существую.»

Пауза.

«Плохие новости: кажется, не весь.»

UI:

**НАЙДИ НУЛИКА**

Игрок должен осмотреть пространство камерой.

Голова Нуля находится не непосредственно перед первоначальным направлением камеры.

Игрок должен повернуться.

---

# 13. HINT SYSTEM

Если игрок не обнаружил объект за заданное время:

например:

`hint_delay = configurable`

система должна помочь.

Возможные подсказки:

Level 1:
звук со стороны объекта.

Level 2:
индикатор направления.

Level 3:
стрелка / более явная подсветка.

Необходимо сделать систему подсказок параметризуемой, чтобы использовать её в других механиках.

---

Нуль:

Пауза.

«Только не спрашивай, где остальное.»

Запускается диагностика.

# 16. COLLECT OBJECTS

По согласованию владельца от 2026-10-09 после DISCOVER головы необходимо собрать три объекта из новой модели. ID null_body сохранён для двигателя:

```text
null_body
null_left_arm
null_right_arm
```

Для MVP расположение может быть заранее заданным относительно AR origin / marker.

Необходимо предусмотреть возможность конфигурировать позиции.

При нахождении/сборе:

```text
1 / 3
2 / 3
3 / 3
```

Каждый объект должен:

- реагировать на выбор;
- исчезать из пространства или перемещаться к Нулю;
- увеличивать счётчик;
- давать визуальный feedback;
- давать звуковой feedback.


После сборки:

Нуль:

# 20. WRONG CHOICE

При неправильном выборе:

не должно происходить Game Over.

Нуль:

«Не он! Ничего страшного, попробуй ещё.»

Объект можно:

- временно деактивировать;
- убрать;
- изменить визуальное состояние.

Игрок продолжает выбирать.

---

# 21. CORRECT CHOICE

После правильного выбора:

визуальный эффект.

Нуль:

«Есть!»

«Вот теперь я снова почти гениален.»

`CORE_FOUND`


После демонстрации:

«Почти. Давай ещё раз.»

# 27. ANOMALY EVENT

Это первый тизер основного сюжетного персонажа / сущности «Аномалия».

Важно:

**не раскрывать Аномалию полностью.**

Не объяснять:

- кто это;
- откуда она;
- является ли она врагом;
- чего она хочет.

Игрок должен получить только ощущение:

**в системе присутствует кто-то ещё.**

---

# 28. VISUAL EVENT

При остановке на `99%`:

1. небольшой glitch;
2. изменение звука;
3. краткое нарушение изображения;
4. внутри портала появляется силуэт;
5. силуэт быстро исчезает.

Нуль:

«Ты это видел?»

Пауза.

На терминале появляется:

```text
СПАСИБО ЗА ДОСТУП
```

Нуль:

«Это написал не я.»

Текст меняется:

```text
УВИДИМСЯ.
```

Портал мгновенно закрывается.

# 30. UX-ТРЕБОВАНИЯ

Это onboarding-игра.

Поэтому:

## Запрещено

- Game Over на первых этапах;
- потеря всего прогресса;
- необходимость начинать игру заново после ошибки;
- сложные длинные инструкции;
- несколько новых механик одновременно;
- наказание ребёнка за неправильный выбор;
- ситуации, где пользователь может надолго застрять без подсказки.

## Требуется

Каждое правильное действие должно давать:

- визуальный feedback;
- звуковой feedback;
- изменение игрового состояния.

Пользователь всегда должен понимать:

**«Моё действие сработало».**

# 32. FAIL-SAFE

Любой этап должен иметь защиту от блокировки прохождения.

Необходимо предусмотреть:


**повторяется текущая механика, а не весь сценарий.**

# 33. DEBUG MODE

Для разработки обязательно предусмотреть простой debug mode.

Он должен позволять разработчику:

- видеть текущий `scenarioState`;
- видеть текущую сцену;
- видеть активную механику;
- видеть progress;
- вручную переходить к следующей сцене;
- перезапускать текущую сцену;
- при необходимости запускать конкретную сцену напрямую.

Например:

```text
DEBUG

Scene: COLLECT_PARTS
Mechanic: COLLECT
Progress: 2/4

[RESTART]
[NEXT]
```

Debug UI не должен отображаться в production mode.

# 37. ASSETS

Не блокировать разработку из-за отсутствия:

- финальной модели Нулика;
- финальной модели портала;
- профессиональной озвучки;
- финальных VFX;
- финальных звуков.

# 44. КРИТЕРИИ ГОТОВНОСТИ MVP

MVP считается технически готовым, если пользователь может пройти полный flow:

```text
SCAN
↓
TOUCH
↓
DISCOVER
↓
COLLECT
↓
CHOOSE
↓
SEQUENCE
↓
ANOMALY EVENT
↓
COMPLETE
```

без вмешательства разработчика.

При этом:

1. Каждая механика запускается корректно.
2. Следующая сцена не запускается раньше времени.
3. Ошибка пользователя не ломает сценарий.
4. Текущий этап можно повторить.
5. Подсказки помогают при бездействии.
6. Все шесть механик являются переиспользуемыми.
7. Assets можно заменить без переписывания gameplay.
8. Тексты можно менять отдельно от механик.
9. Debug mode позволяет тестировать сцены отдельно.
10. Основные gameplay events логируются.
