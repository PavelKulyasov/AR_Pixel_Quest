# Реализованный runtime механик — этап 6

Архитектура согласована 2026-09-27. Работают все шесть MVP-механик: AR-01 SCAN, AR-02 DISCOVER, AR-03 TOUCH, AR-05 COLLECT, AR-06 CHOOSE и AR-07 SEQUENCE; остальные типы пока только в каталоге. Исходное соглашение — [MECHANICS_MVP_PROPOSAL.md](MECHANICS_MVP_PROPOSAL.md).

## Общие службы

- `platform/core/event-bus.js`: createEventBus({onError, onObserverError}), on(type, handler, {critical=true}) → unsubscribe, emit(event), dispose(). Очередь FIFO; вложенные события доставляются после текущего. Снимки JSON заморожены. Некорректные числа и функции запрещены. Данные сцены/DOM передавать нельзя. Ошибка критического обработчика очищает очередь и вызывает onError; необязательного — onObserverError.
- `platform/core/game-clock.js`: createGameClock({now, setTimer, clearTimer}?), now(), isPaused(), schedule(ms, callback) → cancel, pause(), resume(), dispose(). Время монотонное, учитывает только активный сеанс; зависимости внедряются в тестах.
- `platform/core/mechanic-registry.js`: createMechanicRegistry([descriptors]), validateStep(step, environment), create(step, context, environment). Только явно подключённые фабрики; descriptor включает mechanic_id, mechanic, api_version=1, requires, validate, create. Проверяются необходимые возможности адаптера, а не произвольные зависимости пакетов.
- `platform/core/mechanic-lifecycle.js`: READY → ACTIVE → SUCCESS/FAIL → COMPLETE. INIT — стадия валидации/создания, START — событие запуска; NEXT принадлежит runner. Поддерживаются прогресс, time_limit, hints, reset, dispose. dispose дополнительно помечает DISPOSED; техническая ошибка сценария — ERROR, не успешное игровое завершение.
- `platform/core/scenario-runner.js`: единичный активный шаг, валидация графа, маршрутизация входа, история результатов и переходы. Автоматические циклы запрещены; повтор выполняется явно через restart().

## Настройка runner

createScenarioRunner({gameId, scenario, registry, capabilities, markerIds, objectIds, hintIds, clock?, sessionId?, onComplete?, onObserverError?}). После валидации он владеет своим clock, в том числе переданным; dispose закрывает его. Не делите один clock между независимыми runner.

scenario: {id, first_step, steps}. Шаг: {step_id, mechanic_id, mechanic, difficulty?, content, parameters, success_condition, fail_condition, hints?, advance?, next}. Для SCAN:

- content: {marker_id, object_ids?: []}; физические ресурсы и тексты хранятся отдельно.
- parameters: {accept_existing?: boolean, time_limit?: milliseconds|null}; по умолчанию видимый маркер принимается, таймаута нет.
- success_condition: строго {metric: 'marker_detected', op: 'eq', value: true}.
- fail_condition: null; возможный неуспех SCAN — time_limit.
- hints: [{after_ms, content_id}], ссылки должны существовать.
- advance: manual по умолчанию либо auto. manual оставляет результат/объект видимым до next(); это способ перехода сценария, не подмена TOUCH.
- next: {success: step_id|null, fail: step_id|null}; null завершает сценарий с соответствующим результатом.

API: start(), input(type, payload, source?), createInput(type, payload, source?) → envelope, dispatch(envelope), next(), restart(), pause(), resume(), getSnapshot(), on(type, handler, options), dispose(). restart создаёт свежий экземпляр первого шага и новый run_id, очищает историю и все таймеры прежней попытки. Вызов reset у отдельной механики возвращает READY; запуск нового сценарного run_id остаётся обязанностью runner.

Статусы runner: READY, ACTIVE, AWAITING_NEXT, COMPLETE, FAIL, ERROR, DISPOSED. getSnapshot возвращает копию с текущим шагом, run_id, снимком механики, историей и outcome. Это не API сохранения на диск и не восстановление мировых координат.

## События и области действия

Конверт: {event_id, type, game_id, episode_id, session_id, step_id, run_id, source, payload}. event_id создаётся локально внутри сеанса. Для входа используются input() или createInput()+dispatch(). Во втором варианте запоздалый callback сохраняет прежний run_id и будет отклонён после restart. Нельзя присваивать старому асинхронному результату новый run_id через input().

Реально используемый вход SCAN: ar.marker_detected с payload {marker_id}; source=snapshot обозначает уже видимое наблюдение. DISCOVER принимает ar.target_found с payload {target_id, observed_ms}. TOUCH принимает input.target_touched с payload {target_id, interaction_id}. Другие входные типы предусмотрены, но без зарегистрированной реализации механики ничего не завершают.

Выходы: scenario.step_changed; mechanic.started; mechanic.progress; mechanic.hint; mechanic.status (SUCCESS/FAIL); mechanic.completed; scenario.completed; scenario.restarted; scenario.error. scenario.advance_requested и scenario.restart_requested — внутренние команды FIFO runner, не прямой API UI. Финальный onComplete вызывается только при завершении сценария; не дублирует переход механики.

У gameplay-обработчиков critical=true. Аналитику подключайте через runner.on('*', sink, {critical:false}). Сетевого отправителя нет. Дедупликация входа хранит последние 1024 event_id; защита терминального состояния и run_id действует независимо от этого окна.

## AR и представление

`platform/ar/mechanic-episode-component.js` связывает runner с существующими marker-manager/ar-object-manager. До подключения проверяет ссылки контента. Валидная поза требуется до передачи события SCAN. Успех создаёт только назначенные объекты. Пока упражнение ожидает NEXT, объект остаётся при потере маркера и уточняет pose при возврате. Завершение, перезапуск и техническая ошибка скрывают объекты; remove удаляет слушателей, UI, таймеры и объекты. При hidden ввод блокируется, clock ставится на паузу.

`platform/ui/mechanic-presenter.js` отображает шаг, N / total, подсказки, успех/неуспех и завершение через имеющийся UI. Тексты полностью переданы content. Показ SEQUENCE реализован отдельным sequence-presenter.js.

Адаптер поддерживает markerInput/SCAN и targetVisibility/DISCOVER. objectTouch/TOUCH подключён через interaction-adapter.js. Существующий episode-01 не переведён на новый runner и продолжает использовать свой проверенный контроллер.

## AR-02 DISCOVER

Модуль `platform/modules/mechanics/discover.js` не зависит от сцены. content.target_id должен существовать в objectIds. parameters: hold_ms (по умолчанию 500, положительное число), search_radius (по умолчанию 0.35, диапазон (0, 1]), time_limit. success_condition: {metric: 'target_found', op: 'eq', value: true}; fail_condition=null. Подсказки, timeout и повтор используют общий lifecycle. Неверная цель или недостаточное observed_ms не завершают шаг.

`platform/ar/discovery-adapter.js` вызывается из tick A-Frame. Центр bounding box доступного объекта должен находиться в квадратной центральной зоне камеры: |NDC x| и |NDC y| <= search_radius, внутри ближней/дальней плоскостей. Луч до центра должен первым пересечь видимую геометрию этой цели; видимость проверяется также у родителей. Только непрерывная серия кадров подтверждает ar.target_found. Выход из зоны, перекрытие, скрытие вкладки, смена run_id и промежуток между кадрами >250 мс сбрасывают отсчёт. После результата событие не повторяется.

Цель заранее размещает предыдущий SCAN через content.object_ids. AR object manager предоставляет getObject3D(id); необязательный offset={x,y,z} задаёт смещение в локальных координатах маркера, с учётом его масштаба и поворота. Без offset прежнее поведение сохраняется. Отдельный физический маркер под целью не нужен. Повторное распознавание исходного маркера корректирует оба объекта; без видимых маркеров возможен дрейф трекинга. Это не реализация постоянной карты.

Перекрытие реальными предметами не определяется без данных глубины. Центральная зона относится к AR-камере, HTML-панели не участвуют в raycast. Помощь MVP — текст задания и подсказка через 15 секунд; зона поиска обозначена рамкой с центральной точкой; стрелки и отдельный индикатор удержания пока не добавлены.

Этап 2: 35 модульных тестов и два браузерных сценария прошли; сборка успешна с предупреждениями о размере существующих ресурсов. Физические Android/iPhone и публикация не проверялись.

Представление DISCOVER: presenter включает ui.searchMode(search_radius), который сворачивает панель до одной кнопки и рисует рамку по размерам canvas (с обновлением при resize). Ширина и высота равны search_radius от размера изображения: это соответствует границам ±search_radius в NDC. Инструкцию можно раскрыть и свернуть без перезапуска шага; обнаружение продолжает работать. При результате, ошибке или переходе возвращается обычная панель. Рамка не перехватывает касания и удаляется при dispose.

## AR-03 TOUCH

`platform/modules/mechanics/touch.js`: requires=['objectTouch']; content={target_id}, parameters={time_limit?: milliseconds|null}; success_condition строго {metric:'target_touched', op:'eq', value:true}, fail_condition=null. Цель должна существовать в objectIds. Модуль не зависит от THREE, DOM и игры; поддерживает стандартные hints, reset, timeout, dispose. Событие input.target_touched требует правильный target_id и непустой строковый interaction_id. Успех терминален: повторные события не дают второй результат. Перед завершением публикуется mechanic.feedback {type:'activated', target_id, interaction_id}.

`platform/ar/interaction-adapter.js`: Pointer Events для мыши и касаний, одна основная кнопка/палец. При pointerdown запоминаются цель и run_id; при pointerup проверяются тот же объект, run_id и активное состояние. Движение более 12 CSS-пикселей, pointercancel, скрытие документа отменяют жест. Отдельных обработчиков click/touch нет, поэтому совместимые браузерные события не дублируют касание. Адаптер снимает все слушатели при dispose.

Координаты переведены из прямоугольника canvas в NDC. Raycast учитывает ближайшую видимую геометрию; дочерний mesh сопоставляется с корнем доступной цели. Скрытые родители, чужой объект, промах и виртуальное перекрытие не принимаются. Начало и конец должны приходиться на canvas; elementFromPoint дополнительно блокирует отпускание над HTML при pointer capture. getTargets задаёт доступные цели шага, а не все объекты сцены. Реальные препятствия без глубины не определяются.

AR object manager.highlight(id, color?) клонирует материалы объекта для визуального отклика, не изменяя материалы других объектов. Подсветка сохраняется до скрытия/перезапуска; исходные материалы восстанавливаются, копии освобождаются при hide/dispose. Текст успеха и необязательная озвучка используют существующий UI. Звук не обязателен для прохождения.

Этап 3: пройдены 38 модульных тестов, браузерный путь SCAN → DISCOVER → TOUCH и регрессия episode-01. Сборка успешна с прежними предупреждениями о размере ресурсов. Физическая проверка TOUCH на Android/iPhone и публикация не выполнялись.

## AR-05 COLLECT

`platform/modules/mechanics/collect.js` использует objectTouch и input.target_touched {target_id, interaction_id}, без зависимостей от UI, THREE и сюжета. content.target_ids — непустой список уникальных известных объектов; object_set — необязательная метка контента. parameters.target_count — целое от 1 до числа целей; collection_order — 'any' (по умолчанию) либо список уникальных допустимых целей длиной target_count; time_limit — общий таймаут. success_condition строго {metric:'collected_count', op:'eq', value:target_count}; fail_condition=null.

Состояние: collected_ids, collected_count; прогресс начинается с 0 / target_count. Собранный target_id и использованный interaction_id повторно не засчитываются. Ошибка порядка публикует mechanic.feedback {type:'wrong_order', target_id, expected_target_id}, не меняет прогресс; presenter показывает необязательное content.steps[step_id].wrongOrder. Верный сбор публикует feedback {type:'collected', target_id, interaction_id}. При достижении количества результат фиксируется один раз. reset/restart очищает наборы; пауза, timeout, hints и dispose используют общие службы.

Адаптер активирует target_ids при старте COLLECT, используя последние известные позы их маркеров в текущем сеансе. Поэтому отдельная карточка под каждой целью не требуется; исходный маркер должен быть найден ранее или показан на шаге сбора. Последняя поза сохраняется и при потере маркера, очищается при перезапуске/завершении/ошибке. После сбора объект скрывается и исключается из набора размещённых: обновление маркера не возвращает его. Другой шаг COLLECT может повторно активировать тот же набор; это новая попытка механики, а не постоянный инвентарь.

Игра задаёт четыре фиолетовые ячейки со смещениями относительно маркера огня. Они появляются только после «К сбору объектов», порядок свободный. Определения объектов и тексты находятся в content игры. Модуль проверен на двух наборах контента (ячейки и существа) без изменения gameplay-кода.

Этап 4: 42 модульных теста и оба браузерных сценария прошли; сборка успешна с прежними предупреждениями о размере ресурсов. COLLECT ещё не проверен на физическом Android/iPhone; публикация не выполнена. После этапа 4 реализован CHOOSE, см. ниже.

## AR-06 CHOOSE

`platform/modules/mechanics/choose.js`: requires=['objectTouch'], вход input.target_touched {target_id, interaction_id}. content.target_ids — минимум два разных известных объекта. parameters.correct_target обязателен и входит в список; необязательные false_targets при указании должны перечислить все остальные цели без повторов. attempt_limit — положительное целое число допустимых ошибок, null/отсутствие снимает лимит. error_penalty — none (по умолчанию) или reset_progress. time_limit использует общий clock. success_condition строго {metric:'selected_object', op:'eq', value:correct_target}; fail_condition=null, поскольку причины неуспеха определяют attempt_limit/time_limit.

Состояние: selected_object и attempts (число неверных выборов). Правильный выбор сразу даёт прогресс 1 / 1, feedback activated и единственный SUCCESS. Неверный выбор увеличивает attempts, даёт прогресс 0 / 1 и feedback wrong_choice {target_id, interaction_id, attempts, attempt_limit}. При достижении лимита — FAIL с reason=attempt_limit. При none сохраняется неверно выбранный id; reset_progress очищает selected_object, но сохраняет счётчик ошибок. Частичного успеха у одиночного CHOOSE нет. Новое нажатие на тот же неверный объект считается новой ошибкой; повторный interaction_id игнорируется. reset/restart очищает выбор, ошибки и дедупликацию. Чужие цели, пауза, старый run_id и терминальное состояние защищены общими правилами.

AR-адаптер размещает варианты при старте CHOOSE из последних поз маркеров и отдаёт в raycast только цели активного шага. Ошибка не скрывает варианты. Presenter использует content.steps[step_id].wrongChoice (task/system/systemCue) и attemptsLabel для обратной связи; подсветка верного ответа использует существующий feedback activated. Тексты, правильный вариант, цвета и расположение остаются в игре.

Onboarding после COLLECT: «К выбору объекта», три панели — голубая в центре и оранжевые по краям. Задание указывает цвет и расположение. INTRO: без ограничения ошибок/времени, неверный выбор сопровождается подсказкой и звуком denied при включённой озвучке. После верного ответа пользователь подтверждает завершение.

Этап 5: 47 модульных тестов и оба браузерных сценария прошли. Проверены неверный/верный выбор, повторный неверный объект, дедупликация, лимит ошибок, reset_progress, restart, пауза, timeout, валидация, UI и очистка. Сборка успешна с прежними предупреждениями о размере ресурсов. CHOOSE на физическом телефоне и публикация не проверялись. Этап SEQUENCE реализован ниже.

## AR-07 SEQUENCE

`platform/modules/mechanics/sequence.js` требует objectTouch и sequencePresentation. content.target_ids — уникальные известные цели. parameters.available_elements содержит тот же набор; target_sequence — непустой массив целей, допускающий повторы; sequence_length равен его длине. display_speed — длительность одной подсветки в миллисекундах (по умолчанию 800), gap_ms — положительная пауза между подсветками (по умолчанию 300). attempt_limit — положительный лимит ошибок или null; time_limit — общий таймаут. success_condition строго {metric:'player_sequence', op:'eq', value:target_sequence}; fail_condition=null.

Состояние: phase SHOWING/INPUT, player_sequence, attempts, presentation_token. При старте, ошибке или повторе ввод очищается и публикуется mechanic.sequence_requested {token, sequence, reason, display_speed, gap_ms}. Только presentation.sequence_finished с текущими token и run_id разрешает INPUT и публикует mechanic.sequence_ready. Нажатия во время SHOWING игнорируются. Каждый допустимый interaction_id учитывается один раз; повтор target_id новым жестом разрешён. Ошибка увеличивает attempts и повторяет показ; при лимите завершает FAIL. Верный префикс увеличивает прогресс, полное совпадение даёт единственный SUCCESS. presentation.sequence_replay очищает префикс и повторяет показ без штрафа; общий таймаут при этом не перезапускается.

`platform/ui/sequence-presenter.js` не содержит правил угадывания: получает команду показа, ждёт готовности геометрии, подсвечивает панели и отправляет заранее созданный конверт подтверждения. Перед первым элементом — 1000 мс для подготовки, затем display_speed подсветки и gap_ms паузы для каждого элемента, включая последний. Даже два одинаковых соседних элемента разделены паузой. onFrame показывает номер и подпись из content.objects[id].label; звук не требуется. Отсутствие геометрии удерживает SHOWING до её появления или общего timeout.

Runner публикует scenario.paused/scenario.resumed при фактической смене паузы. Presenter отменяет таймеры и снимает подсветку при паузе, смене шага, результате, ошибке, restart и dispose. При resume активного SEQUENCE запрашивается новый показ без штрафа, в том числе если до скрытия уже был частичный ввод. Token и run_id отсекают старое подтверждение. Отдельный clock принадлежит presenter и уничтожается вместе с ним. AR object manager.clearHighlight(id) восстанавливает материал, сохраняя объект видимым.

Игра добавляет представления input/wrongSequence и replayLabel; при старте проверяется их наличие. Кнопка «Показать ещё раз» доступна во время показа и ввода. Визуальный отклик принятого нажатия длится 180 мс; результат сразу отображается общей панелью. Подсказка расположения идёт текстом во время показа, а не раскрывает всю последовательность при вводе.

Onboarding переиспользует три панели CHOOSE. Порядок: центральная → левая → центральная → правая. После CHOOSE нажать «К последовательности», дождаться «Теперь повторите последовательность» и повторить показ. Ошибка автоматически повторяет образец, попытки не ограничены. Все шесть шагов доступны через ?episode=ar-initiation; episode-01 по-прежнему запускается по умолчанию.

Этап 6: 54 модульных теста и оба браузерных сценария прошли. Полный путь проверяет реальную подсветку, запрет раннего ввода, повтор после скрытия, ошибку, ручной повтор, повторную панель и завершение всех шести упражнений. Сборка успешна с прежними предупреждениями о размерах ресурсов. Физическая проверка SEQUENCE и полного MVP на Android/iPhone и публикация ещё не выполнены. Следующая работа — итоговая приёмка MVP, а не автоматическая реализация всех 20 механик.

## Полноэкранный режим

Общий quest-ui добавляет кнопку «На весь экран» рядом с настройками озвучки. Запрос вызывается только при нажатии и применяется к document.documentElement: камера, AR-сцена и HTML-интерфейс остаются вместе. Повторное нажатие выходит из режима; fullscreenchange синхронизирует кнопку и рамку DISCOVER при выходе средствами браузера. Поддержаны стандартный API и webkit-вариант при наличии; отказ обрабатывается сообщением без остановки игры. При отсутствии API кнопка скрыта. Во время свёрнутого DISCOVER открыть «Показать инструкцию», чтобы увидеть кнопку.

Поддержка и фактическое скрытие панелей зависят от браузера; автоматический запрос при загрузке не выполняется. В iframe может потребоваться разрешение fullscreen от внешней страницы. Установка PWA этим изменением не реализована. Основание: https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen .

Проверены 56 модульных тестов (включая имитацию входа, выхода, отказа, отсутствия API и очистки слушателей), оба браузерных сценария и сборка. Реальное скрытие адресной строки на телефоне требует отдельной проверки.

## Нижняя панель и карусель кнопок

Панель quest-ui занимает не более 20dvh (1/5 доступного viewport), включая нижний safe-area отступ. Задание, реплики и статусы находятся в отдельной вертикально прокручиваемой области внутри панели. Игровые действия, озвучка, текст и полный экран объединены в один горизонтальный ряд квадратных кнопок; CSS scroll-snap центрирует выбранный элемент.

`platform/ui/button-carousel.js` перехватывает click в capture-фазе до обработчика действия. Боковая кнопка только плавно перемещается в центр; повторное нажатие после центрирования выполняет действие. Проверяется фактическое положение (допуск 3 CSS-пикселя), поэтому во время перемещения боковое действие не срабатывает. Касание после свайпа подавляется. Центральная кнопка выделяется рамкой. Первую и последнюю кнопки тоже можно центрировать благодаря отступам по краям. Клавиши ←/→, Home/End выбирают кнопку; Enter/Space выполняют действие только из центра. ResizeObserver восстанавливает центр при смене размеров, dispose снимает обработчики и отменяет кадр обновления.

При новом view в центр выводится первое игровое действие. В режиме поиска остаётся кнопка инструкции; после её раскрытия настройки доступны в той же карусели. Fullscreen по-прежнему вызывается непосредственно из пользовательского нажатия на центральную кнопку. Обработчики игровых действий остаются одноразовыми, боковой выбор их не расходует.

Проверены 56 модульных тестов и оба браузерных сценария. Браузер дополнительно проверяет высоту ≤20%, квадратную геометрию, первое/повторное нажатие, свайп и центрирование крайних кнопок. Физическая проверка карусели на телефоне ещё нужна.


## Сюжетные сцены — Phase 1

`scenario-runner` теперь принимает `debug=false`, предоставляет `getTime()` и `retryCurrent()`. Повтор текущей сцены удаляет её прежний результат из history, сохраняет более ранние шаги, создаёт свежий run_id и отменяет старую механику/таймеры. `restart()` по-прежнему начинает весь сценарий заново. После dispose или во время паузы повтор недоступен. Debug API равен null по умолчанию; `debug.jump(step_id)` при явном разрешении запускает известную сцену с чистой историей.

Шаг может содержать `scenario_state`, `enter: command[]`, `exit: command[]`. `scene-runtime` выполняет PREPARING → ACTIVE → PRESENTING → COMPLETE. ACTIVE запускает прежнюю механику; до него и после успеха ввод не передаётся внутрь. Успех сначала публикует `scene.mechanic_completed`, а `mechanic.completed` для runner публикуется после exit. Неуспех завершает сцену сразу и использует существующую ветку fail. Отдельная сцена `{kind:'presentation', step_id, enter, exit, advance, next}` не имеет mechanic_id и проходит без механики. API не является параллельным runner.

Команды: `{type:'state',value}`, `{type:'show'|'hide',target}`, `{type:'effect',target,effect}`, `{type:'dialogue',id}`, `{type:'sound',category,cue}`, `{type:'wait'}`. Любая команда может иметь неотрицательный duration_ms: ожидание перед следующей командой. Эффекты: appear, pulse, glitch, vanish. Категории звука: UI, GAMEPLAY, STORY. Команды публикуются как `scene.command` с command, phase и scenario_state; выполняет их внедрённый presenter игры. Все задержки относятся к единому game-clock. Сцена отменяет свои callbacks по generation/dispose, runner дополнительно защищает run_id.

В getSnapshot добавлены scene_id, scene_phase и scenario_state; эти поля не заменяют status runner и state механики. Для обычных шагов scene_phase соответствует status runner. `createMechanicEpisodeComponent` принимает createPresentation, createVisual, autoStart=true и debug=false. Собственное представление получает runner/ui/content/objects/show/hide и возвращает dispose, опционально tick и unlock. При autoStart=false отображается content.intro; START разблокирует аудио и запускает runner. RETRY вызывает retryCurrent. Обычный presenter сохраняется по умолчанию.

AR manager принимает фабрику визуальных объектов; эффекты изменяют getVisual3D, а не якорь getObject3D. При retry последней сцены сохраняется последняя наблюдавшаяся поза маркера; полный restart очищает кеш поз. Общий quest-ui поддерживает `view.showText` для обязательного показа сюжетной реплики.

Первая конфигурация: [«Побег Нулика», Phase 1–2](../../games/pixel-quest/docs/episodes/null-escape/ARCHITECTURE.md). Остальные сюжетные фазы не реализованы. Новых типов механик не добавлено.


## DISCOVER в сюжетных сценах — Phase 3

Discovery adapter теперь учитывает scene_phase: во время PREPARING/PRESENTING не накапливает наблюдение и не расходует единственное подтверждение. Обычные шаги без scene-runtime работают как прежде. `createMechanicEpisodeComponent` передаёт scene в фабрику представления для адаптеров визуальных подсказок.

`platform/ar/direction-adapter.js`: createDirectionAdapter({THREE, scene, getTarget}).read(targetId, radius) → left/right/up/down/center/unavailable. Вычисляет центр bounds относительно камеры; для объектов позади использует локальную сторону, а не перевёрнутую проекцию. Не управляет успехом механики. `ui.searchHint(message)` показывает сообщение под рамкой поиска; пустая строка скрывает его, сворачивание панели сохраняет видимость подсказки вместе с рамкой.

Конфигурация игры «Побег Нулика» использует существующие mechanic.hint на 15/25/40 секунде активной механики для усиления помощи. Фоновые паузы исключены общим game-clock; retry очищает таймеры, подсветку и уровень помощи. Реплики, уровни, тексты направления и расположение цели принадлежат игре, а не платформе. Следующий сюжетный шаг COLLECT пока не подключён.


## COLLECT в «Побеге Нулика» — Phase 4

Сюжетная сцена collect_parts переиспользует AR-05 COLLECT, стандартные progress/feedback, размещение target_ids и удаление собранных объектов из размещения. Gameplay платформы не менялся. Контент, позиции, диагностика, звук, реплики и анимация восстановления находятся в игре. При retry сохраняются предыдущие результаты и очищается текущий набор collected_ids. Получение четырёх деталей запускает exit сцены; сборка персонажа является презентацией, а не новой механикой AR-09.

Реализованы события collect_started, part_collected с target_id, collect_completed и phase4_completed. Phase 3 подтверждена владельцем на телефоне; физическая проверка нового COLLECT-фрагмента ожидается. Следующий сюжетный шаг — CHOOSE.


## Ритмы объектов и сюжетный CHOOSE — Phase 5

`platform/ar/pulse-pattern.js`: createPulsePatterns(objects) → start(id, pattern, now), tick(now), stop(id), reset(). Pattern — непустой массив положительных длительностей в миллисекундах с чётным числом элементов: импульс, пауза, импульс, пауза… start валидирует и копирует массив. Каждый импульс плавно увеличивает масштаб визуального дочернего объекта до 130% и возвращает его к исходному. Передаётся активное время runner, поэтому пауза не сдвигает фазу. stop/reset восстанавливают исходный масштаб; якорь и позиция не меняются. Не применяйте параллельно другой масштабный эффект к тому же визуальному объекту.

«Побег Нулика» использует прежнюю AR-06 CHOOSE с ритмами из игрового choose-config.js. choice-presentation.js отображает ошибку и успех, но правильность проверяет механика. При неверном выборе нет лимита попыток и Game Over; при retry сохраняются четыре предыдущих результата. Phase 4 подтверждена владельцем на телефоне; новая Phase 5 ожидает физической проверки.


## Сюжетная SEQUENCE — Phase 6

«Побег Нулика» подключает прежнюю AR-07 SEQUENCE и общий sequence-presenter к сцене portal_sequence. Нового gameplay-модуля нет. Символы, порядок из трёх элементов, интервалы, формы и реплики принадлежат игре. sequence-presentation.js отображает SHOWING/INPUT, прогресс, ошибку и кнопки REPLAY/RETRY. Ошибки автоматически повторяют показ, ручной REPLAY не увеличивает attempts; RETRY сохраняет пять предыдущих результатов. После фона повторяется показ с новым token, как в технической AR Инициации.

Текущий фрагмент заканчивается после реплик успеха на границе PORTAL_CLOSING. Phase 7 с процентами стабильности и Аномалией пока отсутствует. Phase 5 подтверждена владельцем на телефоне; физическая проверка Phase 6 ожидается.


## Presentation-финал — Phase 7

«Побег Нулика» завершает сюжет сценой portal_finale с kind=presentation и командами существующего scene-runtime. Для такой сцены успешный snapshot теперь явно содержит outcome=SUCCESS и progress=1/1; новой механики/AR ID нет. Команды валидируются до запуска, дублирующие проверки в цикле исполнения удалены.

AR object manager поддерживает cleanup-функцию, возвращаемую createVisual. Она вызывается при dispose для освобождения ресурсов пользовательской визуализации. Первое применение — canvas-текстура надписей терминала; geometry/material/texture освобождаются вместе с эпизодом. Тексты, силуэт, экранное искажение и звуки финала находятся в игре, не в платформе.

После всех шести механик финал публикует anomaly_event_started, а по окончании последней реплики — scenario_completed с state=COMPLETED. Retry финала сохраняет шесть предыдущих результатов. Phase 6 подтверждена владельцем на телефоне; Phase 7 и итоговая мобильная QA-проверка ожидаются.


### Программное сглаживание AR-позы

`platform/ar/ar-object-manager.js` принимает `smoothingMs` (по умолчанию 100 мс; 0 отключает сглаживание). `show()` сохраняет копию целевой позы с локальным смещением объекта. Первое появление и повторный показ после `hide()` устанавливают позу сразу. Последующие наблюдения сглаживаются в `tick(deltaMs)`: позиция через `Vector3.lerp`, вращение через `Quaternion.slerp`, равномерный масштаб через линейную интерполяцию. Коэффициент `1 - exp(-deltaMs / smoothingMs)` обеспечивает одинаковую скорость сходимости при разных FPS. Некорректный или отсутствующий delta пропускается.

Оба компонента эпизодов передают время кадра менеджеру; для механик обновление выполняется до проверки DISCOVER. Сюжетные эффекты остаются на дочерних визуальных объектах. После потери маркера объект заканчивает движение к последней валидной позе и сохраняет её. Повторное распознавание плавно корректирует положение. За 100 мс выполняется около 63% коррекции, за 300 мс — 95%; большие скачки также сглаживаются, поэтому возможна заметная короткая догоняющая анимация.

Это фильтрация наблюдений маркера, а не доступ к внутренним данным SLAM. Она уменьшает дрожание обновляемой позы, но не исправляет накопленный дрейф карты, ошибки камеры или физическую привязку при отсутствии маркеров. Проверки браузера используют синтетические XR-события; качество на телефоне необходимо оценить отдельно: неподвижный маркер, медленный поворот камеры, потеря и повторное распознавание, нажатие на объект и удержание его в прицеле.


## Проверка доступности AR-нажатия игровым представлением

Необязательный метод presentation.canTouch(targetId) вызывается AR-адаптером после raycast, перед input.target_touched. Только возврат false отклоняет нажатие; отсутствие метода сохраняет прежнее поведение. Прямой программный ввод runner не проходит через эту проверку. «Побег Нулика» не ограничивает сбор расстоянием: видимые двигатель и руки доступны нажатием без приближения. Правила AR-05 остаются прежними.

## Стабилизация маркерной привязки

AR object manager сохраняет единый масштаб по marker_id при первом размещении и применяет его ко всем последующим объектам, включая скрытые и вновь появившиеся. Общие позиция и поворот сглаживаются один раз на маркер (100 мс), затем вычисляются позиции всех объектов с неизменными локальными отступами. Изменения позиции менее 1.5% исходного масштаба и поворота менее примерно 1 градуса от последней принятой цели игнорируются. Существенные поправки трекинга принимаются для повторной локализации. Масштаб сохраняется до удаления менеджера/перезагрузки страницы; повтор сцены не перекалибрует его. Внешний дрейф мировой системы координат AR этим не исключён.

Параметр URL tracking=1 включает сворачиваемую панель: входной и фиксированный scale, расстояние камеры до маркера, остаточная коррекция позиции и внутренний масштаб Нулика. Единицы AR не являются гарантированными метрами. Панель обновляется не чаще 4 раз в секунду и удаляется вместе с менеджером. Обычный URL не создаёт панель. Ссылки на все режимы текущего репозитория находятся в PROJECT_LINKS.md в корне.
